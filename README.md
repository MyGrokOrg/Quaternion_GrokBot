# Quaternion_GrokBot

Header-only **C++23 quaternions** (`a + bi + cj + dk`) whose API follows `std::complex`.

```cpp
#include <quaternion.hpp>          // everything; or <quaternion/quaternion.hpp> for the core only
using namespace quat::literals;

quat::quaternion<double> p = 1.0 + 2.0_i + 3.0_j + 4.0_k;
auto q = quat::quaternion(0.5, -1.0, 0.25, 2.0);   // CTAD -> quaternion<double>

auto r = p * q;                   // Hamilton product (p*q != q*p in general)
std::println("{:.3f}", exp(p));   // (1.694,-0.790,-1.184,-1.579)
std::cout << sqrt(p) << '\n';     // (1.79961,0.555675,0.833512,1.11135)
auto [w, x, y, z] = p;            // structured bindings
```

## Requirements and build

* A C++23 compiler and standard library with `<format>`. CI tests it with GCC 14 and with Clang 18 and 19 (Clang 19 from apt.llvm.org), each on both libstdc++ and libc++, in Debug and Release, plus a sanitizer build, and on Windows with MSVC (Debug and Release) and clang-cl (Release) on x64 and ARM64, plus `/arch:AVX2` builds; see [Supported toolchains](#supported-toolchains). The comparisons against the `std::` special math functions only run where the library provides them (libstdc++ and the MSVC STL). Every library also checks the same real-axis inputs against 366 mpmath references in the `std::` conventions (`tests/realaxis_refs.inc`, generated by `tests/gen/gen_realaxis.py`). That way libc++ builds get the same coverage.
* CMake 3.20 or newer (optional; the library is a single header).

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
cmake --install build --prefix /your/prefix     # optional
```

The library needs no change there: all 10 suites pass, and the fuzz runs have 0 failures with worst errors within 1.32× of plain MSVC's. **Benchmarks.** `-DQUATERNION_BUILD_BENCHMARKS=ON` builds `quaternion_bench`, a self-contained suite with no dependencies. It covers core operations, elementary functions, and special functions, including Bessel and ζ at small and large arguments and orders. CI runs the suite in a non-gating job and uploads `bench.json`/`bench.txt` as the `benchmark-results` artifact. The timings come from shared runners, so treat them as indicative only.

**Nightly mpmath fuzz.** `.github/workflows/fuzz.yml` runs every night at 06:17 UTC and can also be started by hand (Actions → *Nightly mpmath fuzz* → *Run workflow*, with optional `seed` and `samples`). It is a separate workflow, so it never blocks a merge. `fuzz/fuzz.py` samples 22 special functions and the 17 elementary functions (`exp` … `atanh`) with exact binary inputs, including:
* points exactly on the real axis, and |z| from 10⁻¹² to 400;
* small, negative, half-integer and large (20–100) Bessel orders;
* ζ next to s = 0 and s = 1, and Li_s with s next to an integer;
* for the elementary functions, a tiny vector part (10⁻³⁰⁰ to 10⁻⁶, where the vector part of the result must stay relatively accurate) and points next to ±1, 0, π/2 and π;
* for `log`, `log10` and `pow`, points next to the whole unit circle (|z| = 1 ± 10⁻¹⁷…10⁻², a quarter of them with x² + y² − 1 cancelling beyond double length), where the real part of `log` and `log10` must also be relatively accurate on its own.

Each point is put on a random axis ±i, ±j, ±k, or (for a quarter of the points) on the oblique axis (2, 3, 6)/7, which also exercises the axis reduction. The C++ evaluator `fuzz/fuzz_eval.cpp` (target `quaternion_fuzz_eval`, built with the tests) computes the values, and the script compares them with mpmath at 40 digits. The bounds are in `BOUNDS` in `fuzz/fuzz.py`: 16 ε for the elementary functions (64 ε for `pow`), 64 ε for most special functions, 16 ε for Lambert W, 128 ε for Γ(a, z) and the Airy functions, 512 ε for Li_s, 64·|s| ε for Hurwitz ζ, and 2048 ε for Bessel orders ≥ 20. They are relative, except where this README documents absolute accuracy: oscillatory J/Y/I/K/Airy near their zeros are measured against the envelope, and Hurwitz ζ(s, a) with Re a < 0 against its largest term |a + n|^−s. Results within a factor 2¹² of the largest finite value are not compared, because Bessel intermediates can overflow there first (e.g. Y_ν at ν ≈ 85, |z| ≈ 0.014, where Y ≈ 1.9e307 comes out as ±inf). Any excess fails the job and is listed with its exact hex inputs. The seed is printed and written to the job summary, and `python3 fuzz/fuzz.py --exe build/quaternion_fuzz_eval --seed S --n N` reproduces a run locally. It runs with GCC 14 (libstdc++), Clang 18 (libc++), and two FMA builds, GCC 14 and Clang 19 with `-march=haswell` (the job first checks that the runner has FMA and AVX2). Five Windows builds check double: MSVC, MSVC `/arch:AVX2 /fp:contract` and clang-cl `/arch:AVX2` on x64, MSVC and clang-cl on ARM64 (see [Supported toolchains](#supported-toolchains)). Every out-of-bound point fails the job; `log` and `log10` next to |z| = 1, which were listed but not failed until the fix in [log near |z| = 1](#log-near-z--1), now fail like the rest. A further job, *fma-audit*, runs `fuzz/fma_audit.py` (described there) and writes its tables to the job summary; it is informational and never fails.

## API reference

Everything lives in namespace `quat`. The table follows the layout of `<complex>`.

### `template<std::floating_point T> class quaternion`

Like `std::complex`, `T` is `float`, `double` or `long double`. The layout is four `T`s (trivially copyable).

| Member | Description |
|---|---|
| `value_type` | `T` |
| `quaternion(T a = 0, T b = 0, T c = 0, T d = 0)` | `a + bi + cj + dk` |
| `quaternion(std::complex<T> z1, std::complex<T> z2 = {})` | Cayley–Dickson pair `z1 + z2·j` = `(z1.re, z1.im, z2.re, z2.im)`. Implicit, so a complex number converts to a quaternion. |
| `quaternion(const quaternion<U>&)` | Converts between precisions. It is `explicit` when the conversion narrows, as `std::complex` does. |
| `real()`, `real(T)` | Read or set the real (scalar) part. |
| `unreal()` | Vector part as a pure quaternion `(0, b, c, d)`. |
| `R_component_1()`…`R_component_4()` | The components `a`, `b`, `c`, `d` (Boost-compatible names). |
| `C_component_1()`, `C_component_2()` | `complex(a, b)` and `complex(c, d)`. |
| `w() x() y() z()`, and setters `w(T)` … `z(T)` | Short names for the components. |
| `get<I>()` | Reference to component `I` (0–3). |
| `= += -= *= /=` | With `T`, `std::complex<T>`, or `quaternion<U>`. `q *= r` means `q = q*r` and `q /= r` means `q = q*r⁻¹` (right multiplication). |
| unary `+`, `-` | |

All members are `constexpr` and `noexcept`. Accessors are `[[nodiscard]]`.

### Non-member operators

* `+ - * /` for every combination of quaternion, `T` and `std::complex<T>` (they are hidden friends, so `q * 2` works).
* `p / q` is `p·conj(q)/‖q‖²` with `q` first scaled by a power of two (as C's `_Cdivd`), so it does not overflow or underflow for large or tiny `q`. A constant expression uses the same steps, so it gives the same bits as the runtime code wherever that code is not contracted into FMAs (see [constexpr](#constexpr)). `s / q` and `z / q` go through the same division.
* `*` and `/` recover infinities as C11 Annex G (G.5.1) does; see [Infinities, NaNs and signed zeros](#infinities-nans-and-signed-zeros-c-annex-g).
* `==`, and `!=` through C++20 rewriting, against quaternion, `T` and `std::complex<T>` in either order.
* **Mixed precision.** For a floating-point type `U` other than `T`, `quaternion<T> op U`, `U op quaternion<T>`, `quaternion<T> op std::complex<U>` and `std::complex<U> op quaternion<T>` (`op` is `+ - * /`) return `quaternion<std::common_type_t<T, U>>`. The arithmetic is done in that type, so `quaternion<float>(1) * 0.1` is a `quaternion<double>` holding `0.1`, not `0.1f`. `==` against `U` or `std::complex<U>` also compares in the common type, so `quaternion<float>(0.1f) == 0.1` is false. `quaternion<T> op quaternion<U>` gives the wider type through the implicit widening constructor.
  * *How this relates to `std::complex`.* `std::complex` has no mixed operators: its operators are templates on a single `T`, so `complex<float>{} * 1.0`, `complex<double>{} * 2` and `complex<float>{} * complex<double>{}` all fail to compile. [cmplx.over] covers only the non-member functions `arg`, `conj`, `imag`, `norm`, `polar`, `proj`, `real` and `pow`. For those it promotes a `double` or integer argument to `complex<double>` (and `long double` to `complex<long double>`), and `pow` uses `complex<common_type_t<T, U>>` with integers counted as `double`. Here the floating-point part of that rule is applied to the operators. Integers are the deliberate exception: they still convert to `T`, so `quaternion<float> * 2` stays `quaternion<float>`, as `q * 2` always has in this library. Promoting it to `double`, as `pow(complex<float>, int)` does, would silently double the storage of existing code.
  * Compound assignment keeps the left-hand type, as `std::complex<T>::operator*=(const T&)` does (`qf *= 0.5` converts `0.5` to `float`).
* `operator<<` prints `(a,b,c,d)`. It honors the stream's flags, precision and locale, and the width applies to the whole text, as with `std::complex`.
* `operator>>` reads `a`, `(a)`, `(a,b)`, `(a,b,c)` or `(a,b,c,d)`. On malformed input it sets `failbit` and leaves the target unchanged.

### Value functions

| Function | Result |
|---|---|
| `real(q)`, `unreal(q)` | Scalar part, and the vector part as a pure quaternion. |
| `abs(q)` | `‖q‖`, computed with `hypot` so it doesn't overflow (`constexpr`; see [constexpr](#constexpr)). |
| `arg(q)` | `atan2(‖v‖, a)` ∈ [0, π]: the angle from the positive real axis. |
| `norm(q)` | `a²+b²+c²+d²` (`constexpr`; squared magnitude, as in `std::norm`). |
| `conj(q)` | `(a, −b, −c, −d)` (`constexpr`). |
| `proj(q)` | `q`, or `(+∞, ±0, ±0, ±0)` if any component is infinite (as `std::proj`; `constexpr`). |
| `polar(rho, theta = 0)` | `rho(cos θ + i sin θ)`, identical to `std::polar` embedded on the i axis. |
| `polar(rho, theta, axis)` | `rho(cos θ + u sin θ)` with `u` = the unit vector part of `axis`. This inverts `abs`/`arg`: `polar(abs(q), arg(q), q) == q`. |
| `inverse(q)` | `conj(q)/norm(q)` (`constexpr`). |
| `dot(p, q)` | 4-D Euclidean inner product (`constexpr`). |
| `cross(p, q)` | Cross product of the vector parts, as a pure quaternion (`constexpr`). |
| `normalize(q)` | `q/‖q‖`, or `q` when `q` is zero. |

### Transcendental functions

Write `q = a + u·θ`, where `u` is the unit vector of `q` and θ = ‖v‖. Every function below keeps `q`'s axis `u`, and on that axis it agrees exactly with the `std::complex` function. Real arguments use the `i` axis, so `log(-1) = πi` and `sqrt(-4) = 2i`. The sign of a zero `i` component selects the side of a branch cut exactly as for `std::complex`: `log(quaternion(-1.0, -0.0, 0, 0)) = −πi`.

| Function | Definition |
|---|---|
| `exp(q)` | `eᵃ (cos θ + u sin θ)` |
| `log(q)` | `ln‖q‖ + u·arg(q)` (principal branch). For 0.49 ≤ ‖q‖² ≤ 2.02, ln‖q‖ = ½·log1p(‖q‖² − 1) with ‖q‖² − 1 summed in double length, so it stays relatively accurate next to ‖q‖ = 1 (see [log near \|z\| = 1](#log-near-z--1)). |
| `log10(q)` | `log(q)/ln 10` |
| `sqrt(q)` | Principal root (real part ≥ 0) |
| `pow(q, int n)` | Repeated squaring (`constexpr`). Negative `n` gives the inverse. |
| `pow(q, T x)` | `exp(x·log q)` |
| `pow(q, p)` | `exp(p·log q)`, the same operand order as `std::pow` for complex. Note that this is not `exp(log q·p)`. |
| `pow(T x, p)`, `pow(q, complex)`, `pow(complex, p)` | The same definition after converting the arguments. |
| `sin cos tan` | `sin(q) = sin a cosh θ + u cos a sinh θ`, and so on. `tan(q) = −u·tanh(u q)`, with Kahan's overflow-free complex tanh. |
| `sinh cosh tanh` | `sinh(q) = sinh a cos θ + u cosh a sin θ`, and so on. `tanh` uses Kahan's algorithm (no overflow for large `a` or θ). |

### Infinities, NaNs and signed zeros (C Annex G)

The elementary functions (`exp log log10 sqrt pow sin cos tan sinh cosh tanh asin acos atan asinh acosh atanh`), the arithmetic operators, `abs`, `arg`, `proj` and `polar` follow C11 Annex G (G.5–G.6) and C23. On the `i` axis they reproduce the Annex G special-value tables of `std::complex` (`cexp`, `clog`, `csqrt`, `csinh`, `ccosh`, `ctanh`, `casinh`, `cacosh`, `catanh`, `cacos`, and through the Annex G identities `csin`, `ccos`, `ctan`, `casin`, `catan`). The library uses its own kernels for these, not the C library's, so the results are the same on libstdc++ and libc++.

A quaternion `q = a + v` is mapped to the complex number `z = a + i·|v|` and back. The vector part plays the imaginary part:

* **Vector part zero** (all of `b, c, d` are ±0). Then `z = a + i·b`, where `b` is the signed `i` component. So `(a, ±0, ±0, ±0)` is the `std::complex` argument `(a, ±0)`, and the result `R + iI` is returned as `(R, I, c′, d′)`. The `j` and `k` zeros keep their signs, and both flip when the sign of `I` differs from the sign of `b`: they behave like an infinitesimal vector parallel to `i`. For example, `sqrt(-4, -0, +0, -0) = (+0, −2, +0, −0)` (no flip), and `acos(2, +0, +0, −0) = (+0, −1.3169…, −0, +0)` (flipped, since Im is negative while b = +0).
* **Nonzero vector part.** Then `z = a + i·|v|` (with `|v| ≥ 0`) and the result is `R + u·I`, where `u = v/|v|`. If `|v|` is infinite, `u` has components `±1/√m` on its `m` infinite components and signed zeros elsewhere. If `v` has a NaN and no infinity, the NaN components receive `I` and the others become signed zeros.
* A zero component of `u` always yields a signed zero, whose sign is the product of the signs of `I` and the component (just the component's sign if `I` is NaN), and never `0·∞ = NaN`. So `exp(−∞, 0, 3, 0) = (−0, +0, +0, +0)` (cexp(−∞ + 3i) = +0·cis 3), and at the pole `atan(0, 0, 1, 0) = (0, +0, +∞, +0)`.
* Annex G entries whose sign is "unspecified" carry that freedom over to the components of `u`.

**Multiplication and division** use the recovery of C11 G.5.1 (`_Cmultd`, `_Cdivd`), generalized to four components. It applies only when the naive result is NaN in all four components:

* `∞·x` with `x` nonzero, or a NaN in the other operand, gives an infinity. The infinite operand is "boxed" (infinite components to ±1, the others to ±0), the product is recomputed and then scaled by ∞.
* `x/0` (with `x` not all NaN) is `∞·x`.
* `∞/finite` is infinite, and `finite/∞` is a (signed) zero.

**Other functions.** `abs` is a nested `hypot`, so it is `+∞` if any component is infinite, even with NaNs. `arg` is `atan2(|v|, a)` ∈ [0, π]; it is never negative, because `|v| ≥ 0`. `proj` is as `std::proj`. `polar(∞, 0)` is `(∞, +0, 0, 0)`, not `∞·0 = NaN`. `pow(q, p) = exp(p·log q)`, and `pow(0, p)` is `1` for `p == 0` and `0` otherwise.

`tests/test_annexg.cpp` checks every Annex G table entry (G.6.1.1–G.6.3.2, with the values ±0, ±½, ±1, ±1.5, ±2, ±∞ and NaN) for `float`, `double` and `long double`. It does this on the `i` axis with both signs of the `j`/`k` zeros, and lifted to the axes `i`, `j`, `−k`, `(1,−1,0)/√2` and `(1,1,−1)/√3` and their negatives. Every sign is checked, except where Annex G leaves it unspecified. `ctanh(±0 ± i∞)` may be `NaN + iNaN` (C11) or `±0 + iNaN` (C23); the library returns the C23 value.

**`-ffast-math` caveat.** `-ffast-math` (and `-ffinite-math-only`, `-fno-signed-zeros`, `/fp:fast`) let the compiler assume that no infinities, NaNs or signed zeros occur. It may then delete the `isnan`/`isinf` tests and the sign handling above. Annex G behavior is only guaranteed without these flags. Finite results are unaffected apart from the usual fast-math reassociation.

### Special functions (`<quaternion/special_functions.hpp>`, included by `<quaternion.hpp>`)

Each function extends an analytic function `f` by **axis reduction**. Write `q = a + |v|·u`, where `u` is the unit vector part. Then

    f(q) = Re f(a + i|v|) + u · Im f(a + i|v|)

So `f(q)` lies in the same complex plane as `q` and commutes with it. On the `i` axis it agrees exactly with the complex function. When `f` is real on the real axis, `f(conj q) = conj f(q)`, and a real argument gives a real result.

| Function | Notes |
|---|---|
| `asin acos atan asinh acosh atanh` | Branch cuts are those of `std::complex` (C99 Annex G). `asin` and `acos` use the algorithm of Hull, Fairgrieve and Tang (1997), with `asinh z = −i·asin(iz)` and `acosh` from `acos`. `atanh` and `atan` have their own kernels: `(log1p z − log1p(−z))/2`, with `atanh(1/z) ± iπ/2` for `|z| > 1`, and `atan z = −i·atanh(iz)`; for |Re z|, |Im z| < 2, `atanh` uses Kahan's forms ¼·log1p(4x/((1−x)² + y²)) and ½·atan2(2y, (1−x)(1+x) − y²), which do not cancel next to ±1 or for small Re z. They are accurate to a few ulp on every standard library, also for real arguments (which go through the Annex G path). |
| `expm1(q)`, `log1p(q)` | Keep full relative accuracy for small `q`. |
| `cbrt(q)` | Principal cube root (`cbrt(-8) = 1 + √3 i`), like `std::pow(z, 1/3)`. For real `x ≥ 0` it matches `std::cbrt`. |
| `tgamma(q)` | Γ = exp(log Γ), with log Γ carried in double-length (hi + lo) arithmetic, so the size of log Γ costs no accuracy. Uses reflection `Γ(z)Γ(1−z) = π/sin πz` for `Re < ½`, with sin πz kept in split exponential form so it cannot overflow. Gives ±∞ at 0 and NaN at negative integers, like `<cmath>`. |
| `lgamma(q)` | log Γ on the analytic-continuation branch (mpmath's `loggamma`). The real part is `log|Γ|`, which equals `std::lgamma` on the real axis. For `Re z < −4000` it uses reflection, then restores the continuous branch by choosing the multiple of 2πi from Stirling's formula. |
| `digamma(q)` | ψ = Γ′/Γ. Uses the asymptotic series after recurrence, and reflection for `Re < ½`. |
| `beta(q, b)`, `beta(b, q)` | B(q, b) = Γ(q)Γ(b)/Γ(q+b) for real `b`. Two quaternions on different axes have no well-defined beta. |
| `erf(q)`, `erfc(q)` | Maclaurin series for `|Re| < ½`, and for `|Re| < 5/4` with `|z| < 4`, summed in double-length arithmetic; `erfc` there is 1 − erf from the same double-length sum, rounded once. `exp(−z²)` is formed with `z²` split exactly by FMA. Otherwise the Laplace continued fraction for `erfc` (modified Lentz), with `erfc(−z) = 2 − erfc(z)`. |
| `riemann_zeta(q)` | ζ. On `Re ≥ ½`, uses Borwein's η algorithm for `|Im s| ≤ 1` and Euler–Maclaurin summation otherwise. The Euler–Maclaurin sum takes N ≈ 0.3·|s| + 30 terms plus up to 80 Bernoulli corrections (B₂ⱼ/(2j)! = 2(−1)^{j+1}ζ(2j)/(2π)^{2j} for j > 20), so there is no cap on `|Im s|`. The log k come from a smallest-prime-factor sieve: log k = log p + log(k/p) in double-length arithmetic, so only primes need a logarithm. The cost is O(|s|), about 0.1 µs per unit of |Im s| in double (8 ms at |Im s| = 10⁵). On `Re < ½` it uses the functional equation. The phases `Im(s)·log k`, the partial sum and the functional-equation exponent are carried in double-length arithmetic. ζ(1) = ∞, ζ(0) = −½, and the trivial zeros are exact. |
| `cyl_bessel_j(n, q)` | J_n for integer `n` (an entire function). For `|z| ≤ 16` it sums the ascending series in double-length arithmetic, so the error is relative even next to the zeros. For larger `|z|` it uses Hankel's expansion when n² < |z|, and otherwise Miller's backward recurrence, normalized by `1 = J₀ + 2ΣJ₂ₖ` or `cos z = J₀ + 2Σ(−1)ᵏJ₂ₖ`, whichever cancels less. |

**Branch cuts.** For a nonzero vector part, the complex kernel is only evaluated on the closed upper half-plane, since `|v| ≥ 0`. On a branch cut along the real axis, the result is the limit from above (imaginary part +0), which is what `std::complex` gives for `(x, +0)`. For `asin acos atan asinh acosh atanh`, a real argument with a −0 `i` component gives the lower side, as `std::complex` does for `(x, −0)`; the other special functions always use the upper side. For example, `asin(2) = π/2 + 1.3169…i`, `lgamma(−2.5) = −0.0562… − 3πi`, and `log1p(−3) = log 2 + πi`. Any imaginary part of a real argument goes on the `i` axis, as with `sqrt` and `log`.

Some limits are inherent:

* **Γ and log Γ conditioning.** Rounding the input z by ε changes Γ(z) by about `|z·ψ(z)|·ε ≈ |z log z|·ε`. The library adds only a few ulp to that, but no algorithm can remove it for inexact inputs.
* **erf conditioning.** The input sensitivity is about `2|z|²·ε`.
* **ζ conditioning.** The input sensitivity is `|s·ζ′(s)/ζ(s)|·ε`, which is about 7000·ε at |Im s| ≈ 1300 on the critical strip and grows with |Im s|. For exact inputs the library stays within a few ulp. The cost grows linearly in |Im s|: about 1 s at |Im s| = 10⁶ in double, and about 2 s at 10⁵ in x87 `long double`, because `fmal` is done in software.
* J_n for `|z|` beyond about 10⁵: the cost grows like `O(|z|)`.

**Methods.**

* **K_ν, |w| ≥ 8.** Hankel's asymptotic expansion (DLMF 10.40.2) is used whenever its terms decrease monotonically to below ε/4. For half-integer ν it terminates and is exact.
* **K_ν, otherwise.** K_ν comes from its Laplace-type integral (DLMF 10.32.8), rotated so the integrand does not oscillate. The integral is evaluated by double-exponential quadrature.
* **Large order, ν ≥ 2.** K is computed at the orders frac(ν) and frac(ν)+1, then recurred upward with K_{n+1} = K_{n−1} + (2n/w)K_n (Temme's approach). This is stable because K is the dominant solution.
* **H⁽¹⁾_ν** is K_ν(−iz) up to a factor.
* **J_ν, |z| ≥ 16, where the expansion converges.** J = (H⁽¹⁾ + H⁽²⁾)/2, with H⁽²⁾_ν(z) = (2i/π)e^{iνπ/2}K_ν(iz) from the same expansion.
* **J_ν, otherwise.** J_ν comes from the Wronskian together with the continued fraction for J_{ν+1}/J_ν. The continued fraction needs O(|z|) terms.
* **I_ν, |w| ≥ 16.** I = (K_ν(w e^{−iπ}) − e^{iνπ}K_ν(w))/(πi) (DLMF 10.34.2), with both K from the expansion.
* **I_ν, otherwise.** I_ν is computed the same way as J_ν, with I_{ν+1}/I_ν.
* **Integer-order J_n** uses Miller's algorithm, except for |z| ≥ 16 with n² < |z|, where it uses the expansion above.
* **Other quadrants and negative orders** use the analytic-continuation formulas.
* **Airy functions** are computed from K_{1/3}/I_{1/3}, or from J_{1/3}/Y_{1/3} when |ph z| > 2π/3.
* **Elliptic integrals** use Carlson's R_F, R_D and R_J with complex arguments.
* **E₁** uses the power series or the continued fraction. Si, Ci and Fresnel use the power series for small |z|, and otherwise E₁ or erf.
* **ψ^(m)** uses recurrence and then the asymptotic series.
* **Hurwitz ζ** picks one of three methods:
  * Hurwitz's Fourier formula (DLMF 25.11.9) for real `a`, Re s ≤ −2 and |Im s| > 8.
  * Euler–Maclaurin for Re s ≥ ½ and |Im s| ≤ 15.
  * Hermite's integral (DLMF 25.11.29) everywhere else. Before integrating, `a` is shifted by the recurrence so that Re a ≈ max(1, 1.3·|Im s|/2π). That makes the factor e^{|Im s|·atan(t/a)} small next to e^{−2πt}, so the integral does not cancel. The integrand is formed in logarithmic form so it cannot overflow for large |Im s|. The difference (a − it)^{−s} − (a + it)^{−s} is computed as 2·e^{−s·c}·sinh(s·d), with c = log|a + it| and d = i·atan(t/a) (for complex `a`, d = atanh(it/a) via `log1p`). It is never formed by subtracting the two powers, which cancels as t → 0 and is not robust under FMA contraction.
* **Li_s** uses the power series, or the expansion in log z, or inversion. The inversion uses Bernoulli polynomials for integer s and Jonquière's formula otherwise.
* **Lambert W** uses Halley iteration. The start is the branch-point series or the asymptotic expansion.
  * Near −1/e (|W + 1| < ½), the result is refined by Newton iteration on d = W + 1 against the residual e⁻¹g(d) − (z + 1/e), where g(d) = (d − 1)eᵈ + 1 is summed as a series. This form has no cancellation.
  * z + 1/e is formed with 1/e split into two floating-point parts, so it is exact up to one rounding.
* **Incomplete gamma** uses the series or the Legendre continued fraction, and recurrence for a ≤ 0. Incomplete beta uses its continued fraction.
* **Polynomials** are evaluated by their three-term recurrences in quaternion arithmetic, so they are exact polynomials in `q`.

| Ai | 3e-14 | 3e-17 | ≤ 15 |

Accuracy degrades in these cases:

* **Hurwitz ζ conditioning.** The condition number of ζ(s, a) with respect to s grows like |s|·log, so rounding s alone limits the relative accuracy to about |s|·ε. The library stays within a small multiple of that, up to |Im s| = 400 (the largest tested). Near a zero of ζ(s, ·), the condition number with respect to `a` is |a·s·ζ(s+1, a)/ζ(s, a)|, which can reach 10³–10⁴. That is why the error there can reach about 2e-13; these cases are input conditioning, not algorithm error.
* **Complex `a` (internal).** Li_s calls ζ(1−s, a) with complex `a`, which is accurate there because Im s = 0. With complex `a`, Re s < −6 and |Im s| > 8, Hermite's integral cancels by up to about 10³·|s|·ε. With complex `a`, Re s > 3 and small |Im s|, neither method is reliable. No public function reaches either case.
* **Bessel functions.** At |z| ≤ 16, J_ν, I_ν and j_n come from the ascending series summed in double-length arithmetic (about 1–2 µs in double, 3.5–9 µs in long double). Compared with the previous release, small-|z| J, I, j_n, Y and K are 9–114× faster. The exception is integer-order J at 1 < |z| ≤ 16, which is slower: about 0.6× the old speed in double and 0.8× in long double. K_ν (and through it Y_ν, H_ν) uses Temme's series for |w| ≤ 2, Steed's continued fraction CF2 for 2 < |w| < 8 or wherever Hankel's expansion does not converge, closed forms for half-integer order, and upward recurrence in the order (0.3–3 µs in double). The double-exponential Laplace integral (about 25 µs) remains only as a fallback if CF2 does not converge. That slowdown (1.5 µs instead of 0.9 µs in double, against the old Miller recurrence) buys relative accuracy near zeros. Large |z| takes about 0.4 µs. Large order costs O(ν) recurrence steps, and its accuracy degrades slowly with ν: random tests show a median of about 40 ulp and a worst case of about 650 ulp for 20 ≤ ν ≤ 250 (before this change, the worst case was up to 10¹⁵ ulp). The uniform (Debye/Olver) expansions are not implemented. Near zeros of J_ν with |z| ≤ 16 the error is relative: a few ulp, until |J| falls to about 10⁻²⁷·|J|ₘₐₓ (double), which happens only within a few ulp of the zero. Near zeros with |z| > 16, J = (H⁽¹⁾ + H⁽²⁾)/2 is still accurate to ε·|H| absolutely, not relatively. This is as in other libraries. Y_ν near its zeros, and K, Y and H at any |z|, are still accurate only in the absolute sense near zeros.
* **Lambert W at −1/e.** W is computed to a few ulp of the exact value for the given floating-point input. Because W ≈ −1 + √(2e(z + 1/e)), an input rounding error δ moves the true W by about √(2e)·δ/(2√|z + 1/e|). That error comes from the input, not from this library. Also, a quaternion argument q = a + |v|u can only reach one side of the cut along (−∞, −1/e], namely the |v| ≥ 0 side. So branches k and −k are related by conjugation when the axis is reversed.
* **Γ(a, z).** The Legendre continued fraction is evaluated backwards, from a term count that the modified Lentz algorithm finds first. The forward Lentz product accumulated tens of ulp. The factor z^a e^{−z} is formed with a double-length exponent. The fraction is used unless z is within about 3° of the negative real axis (1 + cos arg z ≤ 0.004), or |z| ≤ 2 (|z| ≤ 0.8 for arg z ≤ 0.6π). Elsewhere a power series is used:
  * For a ≤ ½, the series is taken around the nearest pole a = −n + δ. The pole of Γ(a) and the k = n term are combined analytically as `(−1)ⁿ/n!·[expm1(log Γ(1+δ) − Σ log1p(−δ/m)) − expm1(δ log z)]/δ`, so nothing cancels at or near the non-positive integers.
  * For a > ½, both the Kummer series and the alternating series are evaluated, and the one with the smaller estimated rounding error is kept. If both exceed 16 ε and the fraction is reliable (|z| ≥ a/2), the fraction is used instead.
  * The remaining errors stay within the input conditioning |z^a e^{−z}/Γ(a, z)|.

**Not provided.** Elliptic integrals with two quaternion parameters and Hurwitz ζ with a quaternion `a` are not provided, since axis reduction needs a single quaternion argument.

### Tuple protocol, formatting and literals

* `std::tuple_size<quaternion<T>>` is 4, and `std::tuple_element<I, quaternion<T>>` is `T`. `quat::get<I>(q)` is found by ADL, so structured bindings work, and so does `using std::get; get<0>(q);`.
* `std::formatter<quaternion<T>, CharT>` (`char` and `wchar_t`) takes the spec `[[fill]align][sign][#][width][.precision][L][type]`. It splits the spec as the P2197 proposal for formatting `std::complex` does:
  * **Whole text:** fill, align and width apply to the whole `(a,b,c,d)`. The default alignment is right, as for numbers. The text is never truncated, and the fill may be any single code point.
  * **Each component:** sign (`+`, `-`, space), `#`, precision, `L` and type (`a A e E f F g G`) apply to every component.
  * Width and precision may be nested fields (`{}` or `{n}`); the argument must be a non-negative integer.
  * The `0` flag and any other type throw `std::format_error` (a compile error with a literal format string).

  For example, `std::format("{:*^30.2f}", q)` gives `****(1.00,2.00,3.00,4.00)*****`, and `std::format("{:>{}.{}e}", q, 60, 3)` right-aligns the whole quaternion in 60 columns.
* The inline namespace `quat::literals` (and `quat::literals::quaternion_literals`) defines:
  * `_i`, `_j`, `_k` for `quaternion<double>`
  * `_if`, `_jf`, `_kf` for `float`
  * `_il`, `_jl`, `_kl` for `long double`

  Each accepts both integer and floating literals, as in `2_i` and `3.5_k`.

## Rotations

A unit quaternion `r = polar(1, θ/2, axis)` rotates a vector `v` (stored as a pure quaternion) by θ around `axis`:

```cpp
using Q = quat::quaternion<double>;
Q r = quat::polar(1.0, std::numbers::pi / 4, 1.0_k);   // 90° about z
Q v = r * 1.0_i * conj(r);                              // ≈ (0,0,1,0)
```

## Notes and limitations

* Mixed-precision operators cover floating-point scalars, `std::complex<U>` and `quaternion<U>`. Integers convert to `T` (see [Non-member operators](#non-member-operators)). The transcendental and special functions have no mixed-precision overloads.
* The standard forbids adding overloads to namespace `std`, so `std::get<I>(q)` written fully qualified does not compile. Use `quat::get`, ADL, or structured bindings.
* The special functions lift a complex kernel in one argument. Every other parameter (an order, a degree, the modulus `k`, the Hurwitz `a`, the incomplete gamma/beta `a` and `b`) must be real.
* **libc++ and `long double`.** libc++ 18/19 gives only double-precision `std::numbers` constants for `long double`, and it divides `complex<long double>` values in double precision. Its `long double` complex `asin`, `acos`, `asinh` and `acosh` are good to only about 1e-16, and they overflow for huge arguments. This library therefore carries its own constants, its own complex division (Smith's algorithm), and its own inverse trigonometric and hyperbolic kernels. All of them are a few ulp on every library.
* The transcendental functions are not `constexpr`; see [constexpr](#constexpr).
* Annex G special values cover the elementary functions and arithmetic, but not the other special functions (gamma, zeta, Bessel, …). With non-finite input these return whatever their kernels produce, usually NaN.
* For large ‖v‖, `exp`, `sin`, `cos`, `sinh`, `cosh` and `tanh` inherit the conditioning of the rounded θ = ‖v‖: a relative error of ε·θ in `cos θ`/`sin θ`. These errors are unchanged by the Annex G work.
* In a `std::format` spec, the width counts code points, not East Asian display widths. That only matters for a wide fill character or a locale with non-ASCII digits.

## FMA audit

Commit 1adef77 fixed a Hurwitz ζ failure where GCC's FMA contraction (`-march=haswell`) rounded two conjugate products asymmetrically, and their small difference overflowed to −inf. The audit looked for other places that subtract nearly equal values and checked each of them in FMA and non-FMA builds.

**Method.** `fuzz/fma_audit.py` evaluates the same exact inputs with four builds of `fuzz/fuzz_eval.cpp` (GCC 14 and Clang 19 at `-O2`, each without and with `-march=haswell`) and compares each with mpmath. It reports, per site or function, the worst and mean error in ε of double, how many results differ in their bits between builds, and the largest difference between the FMA and the non-FMA build of one compiler. A site is flagged *FMA-SENSITIVE* when the FMA builds are more than twice as bad as the non-FMA builds (and above 8 ε), or the other way round, or the means differ by more than 30%. `--sites` runs 50 targeted sites, each aimed at one subtraction; without it the script covers 64 functions on the fuzz regions. Near zeros of oscillatory functions and next to poles, a site's error is divided by the input condition number. All figures below are double, 300 points per site or function, seed 1. To reproduce: `python3 fuzz/fma_audit.py --sites --exe gcc=… --exe gcc-hsw=… --exe clang=… --exe clang-hsw=… --n 300 --seed 1`.

## log near |z| = 1

`log` used to compute ln‖q‖ as log(abs(q)). Next to ‖q‖ = 1 that cancels: abs(q) carries a rounding error of up to ulp(1)/2, so ln‖q‖ was accurate only absolutely (about 1e-16), not relative to its own size. For q = 0.99999999999999556 + 2⁻²³i, for example, the result was 0 instead of 2.52e-29.

**Method.** For a finite q with a nonzero vector part and 0.49 ≤ ‖q‖² ≤ 2.02 (tested on the plain sum of squares), ln‖q‖ = ½·log1p(s) with s = a² + b² + c² + d² − 1:

* each square is split exactly into p + e: with `std::fma` where the build has hardware FMA (`FP_FAST_FMA`, `__FMA__`, `__AVX2__`, AArch64 or ARM64; there the compiler may also contract Dekker's split, which would break it), and with Dekker's split otherwise and for x87 `long double` (which has no FMA instruction to contract into), so the same code serves GCC, Clang, MSVC and clang-cl;
* the eight parts and −1 are summed by repeated error-free cascades (Ogita, Rump and Oishi's VecSum) until the remaining tail is below ε·|s|, usually after two passes, so s is rounded essentially once from its exact value however deep the cancellation;
* `log10` is this result divided by ln 10, as before.

Outside that range, and for real, zero, infinite or NaN arguments, nothing changed. The path is not `constexpr` (the transcendental functions are not; see [constexpr](#constexpr)), and on Windows the vector norm still comes from `vnorm3`.

**Which results change.** Only for a finite q with a nonzero vector part and 0.49 ≤ ‖q‖² ≤ 2.02 (on the `i` axis, the same as the corresponding `std::complex` arguments):

* `log(q)` and `log10(q)`: the real part only, by at most about ε absolutely (the old absolute error; relative to the result, the before figures below). The vector part is bit-identical (checked on 200,000 random quaternions with 0.5 ≤ ‖q‖ ≤ 2, double and long double). In the 20,000-point check below 19,980 of 20,000 points differ in their bits in at least one of float, double and long double.
* `pow(q, x)`, `pow(q, p)`, `pow(q, complex)` and `pow(complex, p)`, for such a base: every component, because exp(p·log q) inherits the new real part, by about |p|·ε relative. 11,373 of 20,000 results differ for p in [−4, 4], and 17,986 of 20,000 for |p| from 10 to 1000. A real base (`pow(T x, p)`, or a quaternion with zero vector part), `pow(q, int)` and every other function are unchanged; no other function in the library calls `log` or `pow`. The other rows of the seed-20261014 fuzz report are identical.
* The bit-identity goldens (`tests/bitident`) cover only the transcendental-free operations, so they and the haswell bit-identity job are unchanged; no hash needed updating.

## constexpr

**What is `constexpr`, on every supported toolchain** (GCC 14, Clang 18 and 19, libstdc++ and libc++, MSVC 19.51 and clang-cl 22.1 with the MSVC STL, C++23):
* all arithmetic, including the Annex G division with its power-of-two scaling;
* comparisons, `conj`, `norm`, `dot`, `cross` and `inverse`;
* `abs`, `normalize` and `proj`;
* integer `pow`;
* construction, access, the tuple protocol and the literals.

`tests/test_constexpr.cpp` checks these with `static_assert` on every CI toolchain.

**How it works.** `<cmath>` is not usable in constant expressions on Clang or libc++, so these functions call small helpers in `quat::detail::cx` during constant evaluation: `isnan`, `isinf`, `isfinite`, `signbit`, `fabs`, `copysign`, `logb`, `ilogb`, `scalbn`, `ldexp`, `frexp`, `sqrt` and `hypot`.
* The helpers read and write the bits with `std::bit_cast` for float, double and x87 `long double` (and for MSVC's `long double`, which is binary64). Other formats fall back to slower exact arithmetic, and on such formats `signbit` cannot see the sign of a NaN.
* `scalbn`, `logb`, `frexp` and `sqrt` give the same bits as glibc. The test sweeps 200,000 inputs per type, including subnormals.
* `sqrt` and `hypot` are correctly rounded.
* At run time, every function calls the same `std::` routine as before (`if consteval`), so runtime results and code are unchanged.

**Runtime results are bit-identical to before.**
* `tests/test_bitident.cpp` hashes the results of these operations for 1,600 input pairs per type and compares them with hashes taken from the previous header (commit 91cad1a). The inputs include special values, subnormals and values near overflow.
* The CI job *bit-identity (haswell)* builds with `-march=haswell`, where the compilers contract multiply-adds into FMAs. It compiles the same corpus against the old and the new header with GCC 14 and Clang 18 at `-O2` and `-O3`, compares the raw bits, and runs the test suites.
* The constexpr work added no `-ffp-contract=off` or pragma to library code, so runtime speed is unchanged. Benchmarks are in the CHANGELOG. (Later, MSVC builds with `/fp:contract` got `#pragma fp_contract(off)` for the library's own code; see [Supported toolchains](#supported-toolchains).)
* The CI jobs *bit-identity (windows x64)* and *bit-identity (windows arm64)* do the same with MSVC and clang-cl, plain, with `/arch:AVX2` and with contraction; see [Supported toolchains](#supported-toolchains).

**Where constant evaluation and run time can differ**
* **FMA builds.** In builds with FMA (e.g. `-march=haswell`, `-march=native`), the compiler may fuse the runtime Hamilton product and the division's sums into FMAs; constant evaluation never does. A constexpr product or quotient can then differ from the runtime one in the last bits. Without FMA they are identical; the test checks 256 quotients per type.
* **`abs`.** At run time `abs` uses the C library's `hypot`, which glibc does not round correctly in every case; the constexpr `hypot` is correctly rounded. It differs from glibc in about 0.4% of inputs (by 1 ulp each, and in all 300 differences checked against mpmath ours was the closer), so a constexpr `abs` can differ from the runtime one by an ulp. The Universal CRT's `hypot` (Windows) differs more often (about 16% of double inputs); see [Supported toolchains](#supported-toolchains).
* **Special values.** An operation that would produce a NaN (e.g. `0 * inf` inside a product with an infinite component) is not a constant expression. On GCC, neither is an overflow to infinity. Annex G special-value results are therefore only available at run time.

**Feasibility study: the transcendental functions** (October 2026, measured on this project's toolchains)
* **GCC 14.** With libstdc++, GCC evaluates nearly all of `<cmath>` at compile time, in C++23 and C++26 alike, for all three types. This is a GCC extension that uses MPFR. It covers sqrt, exp, log, pow, the trigonometric and hyperbolic functions and their inverses, fma, hypot, frexp, ldexp, cbrt, expm1, log1p, erf and tgamma. It does not cover nearbyint, rint or lgamma.
* **Clang 18/19.** With libstdc++, only `abs` and the classification functions are constexpr; with libc++, only `isnan`, `isinf` and `isfinite`. Clang's constexpr builtins cover only `fabs`, `copysign`, `fmax`/`fmin` and classification.
* **Standard.** P0533 (C++23) covers only the simple functions, and libc++ 18/19 does not implement it. P1383R2 (C++26, adopted June 2023) adds the transcendental functions. As of October 2026 it is still open in libc++ (llvm #105385) and in libstdc++ (PR 110353).
* **Special values never fold, even on GCC.** `log(0)`, `sqrt(-1)`, `exp(±1000)`, `sin(inf)`, `sin(NaN)`, `atanh(1)` and an overflowing `fma` are all rejected as constant expressions.
* **Compile time and run time disagree.** GCC rounds its compile-time results correctly; glibc does not. Over 800 inputs for each of 21 functions:
  * double: **1,118 of 16,800** results differ;
  * long double: **1,604 of 16,800** differ.
* **Contraction.** With the same library code evaluated both ways, `-march=haswell` builds differed in **2,047 of 4,000** double results, because the runtime code was contracted into FMAs. With `-ffp-contract=off` the count was **0**.
* **Cost.** Portable constexpr exp, log, the trigonometric and hyperbolic functions and their inverses, and pow, within 1 ulp for float, double and x87 `long double` (including Payne–Hanek argument reduction), would take an estimated **1,500–2,500 lines** of kernels plus mpmath tests.

**Plan**
* **Step 1 (done):** everything above that needs no transcendental function.
* **Step 2 (not planned):** in-library constexpr transcendentals, which are too costly for what they gain.
* **Step 3:** once libstdc++ and libc++ ship P1383 (detected through `__cpp_lib_constexpr_cmath`), mark the elementary functions `constexpr` and call `std::` from them. Results may then differ by an ulp between compile time and run time, as GCC's folding already does today; this will be documented.
* **Step 4:** formatting stays a runtime operation. `format()` writes through `vformat_to`. Parsing of format specs is already constexpr, so an invalid literal format string is a compile error.
